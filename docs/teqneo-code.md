# Teqneo Code

"Teqneo Code" is [T3 Code](https://t3.codes) — the open-source app that drives
the coding agents a person is already signed in to — set up and dressed for
Teqneo: tied to the PM tool and the hub ([code-handoff.md](code-handoff.md)),
and in the Teqneo look. It comes in two layers: a theme for stock T3 Code, and
Teqneo's own build of the app. Both are done.

## Layer 1 — the look, on stock T3 Code (done)

T3 Code takes custom themes: a palette for its 61 colour roles, light and dark,
plus custom CSS. `t3/teqneo.json` is Teqneo's, generated by
`t3/build-theme.mjs` from the same design-system tokens the hub uses
(`apps/web/src/app/globals.css`):

| | Light | Dark |
|---|---|---|
| Ground | paper `#f1ebdd`, sidebar paper-2 | black `#0b0b0b` |
| Work surfaces | white | `#171614` |
| Primary action, send | black, red on hover | paper, red on hover |
| Focus, updates | AI blue | AI blue, lifted |
| Errors, warnings | red (the palette has no amber) | red, lifted |
| Shape | square corners (2px on inputs), Helvetica — via the theme's CSS | same |

```
node t3/build-theme.mjs           # regenerate t3/teqneo.json
node t3/build-theme.mjs --check   # fail if stale, or if T3 Code would refuse it
```

The builder checks what T3 Code's own parser checks, so a theme it writes is a
theme T3 Code accepts: every role present as `#rrggbb` (the role list is T3
Code's, compared against its source), a name under 48 characters, CSS under
50,000 characters that loads no files, and variants that do not repeat the base
appearance — T3 Code rejects a whole theme over that last one.

**Installing it.** `node scripts/setup-claude-code.mjs … --with-t3` publishes it
as a T3 Code *environment theme* — `~/.t3/userdata/themes/teqneo.json`, then
`t3 theme set teqneo` — so this machine's T3 Code switches to it once. Choosing
another theme afterwards sticks; it is a default, not a lock. By hand: Settings →
Appearance → Add theme, and paste the file.

**Verified.** The generated theme was imported into T3 Code's web app
(app.t3.codes): accepted, both appearances, and the app renders in paper and
black with the black primary action. One gap: that hosted build stores imported
themes without their CSS, so the corners stayed T3 Code's rounded ones there.
T3 Code's own source keeps the CSS on import and publishes it with environment
themes, which is the route the setup script uses — but the square corners and
Helvetica are **not yet seen working** until it runs on a machine with T3 Code
installed.

## Layer 2 — the app itself (the fork; built)

Teqneo Code is also a fork of T3 Code, kept on the `teqneo` branch of
`thor1033/teqneo-code` (to be created; until then it is a local clone).
Everything that differs from T3 Code lives in its `teqneo/` folder and is
applied by one script, `teqneo/apply-branding.py`, so it can be re-applied
after each upstream update (`teqneo/sync-upstream.sh`). `--check` reports
anything missing, and the script stops rather than half-apply when upstream
has moved a line it changes.

| | |
|---|---|
| Name and icon | "Teqneo Code" everywhere a person reads it; the Teqneo mark in the app, the window and the installer |
| Look | the Teqneo Design System (paper, black, red on hover, AI-blue focus, square corners, Helvetica, micro-caps buttons) in one stylesheet the fork owns |
| Its own environment | `~/.teqneo`, its own app-data folder, the `teqneo` command, the `teqneo-code://` link scheme and app id `co.teqneo.code`, so it can sit beside a T3 Code install |
| Nothing to T3 | a built-in Teqneo policy turns off T3's hosted relay and usage data ("Managed by Teqneo"); the GitHub-star prompt is off; links point at Teqneo |
| Updates | off until Teqneo publishes its own releases |

The PM tool's **Start in Teqneo Code** opens `teqneo-code://new?prompt=…`,
which the installed app registers with the operating system.

**Building it** needs Node 26 and pnpm 12 (`pnpm install`, `pnpm dev:desktop`,
`pnpm dist:desktop:win`); the fork's `teqneo/README.md` has the steps.
Unsigned installers warn on first run until Teqneo has Windows and Apple
signing certificates.

**The cost** is unchanged: T3 Code moves fast, so someone re-applies the
branding to each upstream release, builds it and publishes it. The script
makes that one command; deciding what to do when upstream moves a line stays
a person's job.

Layer 1 still applies to anyone using stock T3 Code.

## Work: meetings, tasks and the agent each is meant for

The flow: a meeting is transcribed, the Secretary proposes what it changed on
the PM board ([secretary-agent.md](secretary-agent.md)), a person approves, and
the team sees in Teqneo Code who picks up what. Teqneo Code opens on **Work**,
which has two tabs.

**Tasks** lists a PM project's open tasks, arranged by the agent each is meant
for: Code first, then each hub agent, then "No agent yet" (or by status). The
agent is the PM tool's `agent` on a task: a hub agent's slug, or `code`. The
Secretary sets it when it files a task from a meeting, only on a clear fit;
anyone can change it in the PM tool's task window. **Start** on code work
opens a draft with the same brief the PM tool's "Start in Teqneo Code" writes,
its `PM-Task:` line included, so the pull request's merge proposes closing the
task on `/approvals`. **Ask** on a task meant for a hub agent opens a draft
that hands the task to that agent through the hub; what the agent wants to
write waits for approval, and the draft tells the thread not to approve for
the person. The page only reads the board: a task's status is changed in the
PM tool, or by the agent in the thread when asked.

**Meetings** shows what the Secretary proposed from recent meetings, one block
per run: each change to the board, whether it still waits, and the agent its
task is meant for. A waiting change is approved or rejected in place; one
already made can be started from there.

The page reads through Teqneo Code's own server, which calls the hub as the
person with their hub credential (`HUB_TOKEN`, or the `ai-hub` connection
Claude Code already holds):

| Tool | Gives |
|---|---|
| `hub_team_overview` | the agents, and the approvals waiting |
| `hub_team_projects`, `hub_team_tasks` | the board, through the hub's read-only PM-tool connection, as `hub_team_board` reads it |
| `hub_team_meetings` | the Secretary's held writes, grouped by run |
| `hub_decide_proposal` | approve or reject one |

`hub_team_meetings` shows a person what `hub_list_proposals` would: the
writes they may decide, all of them for an admin. It never returns a run's
prompt (the transcript), and a run that read confidential material keeps its
arguments and result in the hub ([sensitivity.md](sensitivity.md)); the page
then shows only the reason. The hub's pass-through of the PM tool itself
(`pm_*`) is only for a person signed in through the browser, whose own token
it forwards; a hub credential has none to forward, so it is not used here.

## The hub, inside Teqneo Code

The **Hub** page (the people icon in Teqneo Code's sidebar footer) gives the
overview the hub's own pages give, as the person, from inside the code:

| Tab | What | Acts |
|---|---|---|
| Agents | the org chart by function: each agent's owner, where it runs (hub, Claude Code, both), who decides its writes, skills, schedules | **Call** opens a draft that asks it through the hub |
| Approvals | the writes waiting for you | Approve, Reject |
| Schedules | every agent's schedules, yours first | pause and resume yours; set an agent on a clock |
| Team | each person's open PM work (late first), what waits on whom (admins), who owns which agents | |

It reads the hub's team tools (`lib/mcp/teamTools.ts`: `hub_team_overview`,
`hub_team_board`, `hub_schedule_create`, `hub_schedule_set_enabled`) plus
`hub_list_proposals` and `hub_decide_proposal`, through one route on Teqneo
Code's own server (`POST /api/teqneo/hub`) that adds the person's hub
credential: `HUB_TOKEN`, which the setup script stores in
`~/.claude/settings.json`. The browser never holds it, the route passes only
those six tools, and the hub decides what the credential may see and do.
Without a credential the page says to run the setup.
